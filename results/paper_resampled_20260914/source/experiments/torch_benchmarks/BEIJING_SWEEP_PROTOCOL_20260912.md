# Beijing PDE learning-rate screening and paired confirmation

The user authorized designing and launching a bounded parallel tuning round on Beijing supercompute on 2026-09-12. This campaign searches the learning rate while preserving the four-hidden-layer tanh network, width 128, batch 400, PDEs, constraints, losses, Adam settings, eager execution, float32, and 1200-second training budget of the completed T4 experiments. Beijing uses V100 and PyTorch 2.5.1+cu121, so its throughput is measured within its own paired confirmations; raw runtimes are not pooled with T4 results.

`bscc_sweep_plan.json` is the frozen configuration. Both KdV problems screen constant learning rates 1e-5, 1e-4, 3e-4 and 1e-3. CH screens 1e-4, 3e-4, 1e-3 and 3e-3. Twelve independent screening jobs use the shared-jet implementation, one seed and common fresh validation points. The array order interleaves the three PDEs at each learning-rate index, with at most three single-GPU jobs running concurrently.

Selection uses only the final iterate and the root-mean-square of the space-time and terminal relative-L2 errors, giving both evaluation domains equal weight. Validation seeds 20261201/2/3/99 are separate from training and from the confirmation test seeds 20261301/2/3/99. The existing T4 evaluation stream is preserved as the default of the original training command. No checkpoint is selected for its validation loss, and exact interior values are never training labels.

After all screening jobs terminate, each PDE selects its best complete finite checksum-verified candidate. A second array, again capped at three GPUs, runs coordinate JVP and shared jets sequentially on the same allocated V100 with a fresh initialization/sampling seed 20260919 and a separate test stream. Method order alternates across PDEs. All selected comparisons use the same learning rate, initialization, sampled-batch prefix, boundary implementation and evaluation points within each pair. The new-seed confirmation, rather than the screening winner's error, is the primary report of the selected setting. A single confirmation seed is a replication check, not a multi-seed statistical estimate.

The main training budget is 18 runs x 1200 seconds = 6 GPU-hours. The scheduler imposes 15 minutes for one GPU preflight, 30 minutes for each of 12 screen jobs, and 60 minutes for each of three confirmation jobs: at most 9.25 allocated GPU-hours including all allowed initialization, tests and diagnostics. Child processes have a 1500-second limit. There are no automatic retries or budget extensions. Failure or nonfinite tensors exclude a candidate; no eligible candidates means no confirmation for that PDE.

The preflight runs the project tests, verifies actual V100 allocation and pinned dependency versions, exercises all six PDE/method pairs at full width and batch for two updates, checks loss and parameter-gradient agreement on the V100, and saves/restores each checkpoint for a further finite update. Training arrays may queue behind a Slurm afterok dependency on the frozen preflight job. Each GPU worker additionally verifies the sealed preflight PASS gate before training. The confirmation array depends on both successful preflight and termination of all screen jobs. Invalid dependencies are cancelled by Slurm. A preflight success does not establish training convergence.

A checksummed source snapshot records its original Git commit and every delivered source file. Every worker verifies this snapshot and its own device/runtime. The existing Beijing Python environment is reused read-only; no other project's environment or data is modified. Work, checkpoints and logs stay in the unique campaign directory under the assigned run filesystem. Every completed training cell is sealed with SHA-256 hashes. Each confirmation checks final artifacts, changed finite parameters, matching sampled prefixes, evaluation sets, and saved prediction errors before reporting COMPLETE.

Use `bscc_sweep.py` to submit the preflight, then submit the two campaign arrays. `screening/`, `confirmation/`, `selection/`, `preflight/`, and `logs/` preserve distinct evidence. `report` summarizes partial or complete state without submitting work. Complete-job exit records and summaries, not merely job IDs, establish completion. The manuscript is not changed automatically by this campaign.
